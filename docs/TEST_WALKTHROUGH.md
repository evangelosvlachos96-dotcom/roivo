# Debugging Walkthrough

A checklist of actions to perform in Visual Studio with the debugger
attached. Each action lists what to do, where to set breakpoints, and
what to observe. The goal: by completing this list you'll have seen
every major code path execute and built mental models for each.

Estimated total time: 90–120 minutes. Take breaks. Skip flows you
already understand.

## Setup

1. Open `Roivo.sln` in Visual Studio.
2. Set **Roivo.Web** as the startup project.
3. Confirm PostgreSQL is running locally (connection string in
   `src/Roivo.Web/appsettings.Development.json` → `ConnectionStrings:Default`).
4. Apply any pending migrations:
   `dotnet ef database update -p src/Roivo.Infrastructure -s src/Roivo.Web`.
5. Open Mailtrap (the dev SMTP relay — credentials in
   `appsettings.Development.json` → `Smtp`).
6. Open pgAdmin (or your DB client of choice) pointed at the `roivo` database.
7. Press F5 to start with debugger.

Set `Just My Code` **off** in Tools → Options → Debugging if you want
to step into ASP.NET Identity. Otherwise leave it on for a tighter loop.

## Test 1: Register a new user

**Goal:** see how registration creates an Identity row + a `Tenant` and
fires the confirmation email via Hangfire.

**Steps:**
1. Navigate to `/Account/Register`.
2. Set breakpoints:
   - `src/Roivo.Web/Areas/Account/Pages/Register.cshtml.cs` → `OnPostAsync` first line.
   - The line where `new Tenant { ... }` is constructed (around the `_db.Tenants.Add(tenant)` call).
   - The line `_backgroundJobs.Enqueue<EmailJob>(...)` (confirmation email).
3. Fill the form. Use a fresh address like `test+1@example.com`.
4. Submit.

**Watch for:**
- ModelState validation passing.
- `UserManager.CreateAsync(user, password)` returning `Succeeded == true`.
- The new `Tenant` entity having the form's organization name + AFM + type.
- Email confirmation token generated by `UserManager.GenerateEmailConfirmationTokenAsync`.
- Hangfire returning a job ID for the email enqueue.
- `AuditAction.UserRegistered` written.

**Verify in pgAdmin:**
- New row in `AspNetUsers` (note `EmailConfirmed = false`).
- New row in `Tenants` (correct `Type`, `Afm`).
- `AuditLogs` has a row with `Action = 'UserRegistered'`.

**Verify in Mailtrap:**
- Confirmation email arrived with a `/Account/ConfirmEmail?...` link.

## Test 4: Create a business

**Goal:** see the canonical handler shape (null-guard → permission → load → validate → mutate → save → audit).

**Steps:**
1. Navigate to `/businesses` (logged in as an Accountant tenant — the default; Business-type tenants cannot create per `BusinessPermissions.CanCreate`).
2. Click "Δημιουργία επιχείρησης".
3. Set breakpoints:
   - `src/Roivo.Web/Components/Pages/BusinessCreate.razor` → the submit handler.
   - `src/Roivo.Application/Features/Businesses/Commands/CreateBusiness/CreateBusinessHandler.cs` → `Handle` first line.
   - `BusinessPermissions.CanCreate` (in `src/Roivo.Core/Domain/Businesses/BusinessPermissions.cs`).
   - `Business.Create` factory in `src/Roivo.Core/Domain/Entities/Business.cs`.
4. Fill with a valid AFM (e.g. `094014201` — passes the Greek checksum). Submit.

**Watch for:**
- Permission returns `true` for Accountant.
- AFM validator passing.
- `IBusinessRepository.AddAsync` running `INSERT`.
- `AuditAction.BusinessCreated` written **after** the save succeeds.
- Return variant: `CreateBusinessResult.Success(BusinessId)`.

**Try the failure paths too** (set breakpoint and re-submit):
- Invalid AFM → `CreateBusinessResult.InvalidAfm`.
- Duplicate active AFM → `CreateBusinessResult.ActiveDuplicate(afm)`.
- Duplicate inactive AFM → `CreateBusinessResult.InactiveDuplicate(existingId, oldName, oldAddress)`.

**Verify in pgAdmin:**
- New row in `Businesses` with `TenantId` matching your session.
- `AuditLogs` has `BusinessCreated`.

## Test 5: Connect AADE

**Goal:** see the credential-validation round-trip + the encrypted store.

**Steps:**
1. From `/businesses`, click your new business → AADE myDATA → **Σύνδεση με AADE**.
2. Set breakpoints:
   - `src/Roivo.Web/Components/Pages/BusinessAade.razor` → `HandleConnect`.
   - `src/Roivo.Application/Features/Aade/Commands/ConnectAade/ConnectAadeHandler.cs` → `Handle` first line.
   - `src/Roivo.Aade/AadeHttpClient.cs` → `ValidateCredentialsAsync`.
   - `src/Roivo.Aade/EncryptedCredentialStore.cs` → `StoreAsync`.
3. Use real AADE dev credentials if you have them, or programmable fake ones to hit the failure branches first.

**Watch for:**
- Validation result variant: `Success`, `InvalidCredentials`, `AfmMismatch(credAfm)`, `RateLimited`, `NetworkError`, or `AadeServerError`.
- On `Success`: `StoreAsync` calls `IDataProtector.Protect` before INSERT. The ciphertext is what hits the DB.
- `business.ClearAadeSyncFailure()` runs (so any prior failure-banner clears).
- `AuditAction.AadeConnected` written; details exclude the credentials.
- On `AfmMismatch`: `AuditAction.AadeConnectionAfmMismatch` written for forensics.

**Verify in pgAdmin:**
- `Businesses.AadeUserIdEncrypted` + `AadeSubscriptionKeyEncrypted` are non-null ciphertext (NOT plaintext).
- `Businesses.HasAadeFailure = false`.

## Test 6: Sync AADE invoices

**Goal:** the meaty one — orchestration across handler + credential store + HTTP client + multiple repositories + audit. Full walkthrough lives in `docs/FLOWS.md` § Flow 2.

**Steps:**
1. On the AADE page of a connected business, click **Συγχρονισμός τώρα**.
2. Set the 10 breakpoints listed in `docs/FLOWS.md` § Flow 2 — Breakpoints.

**Watch for:**
- Decrypted credentials are non-empty (verify, don't copy).
- AADE call surfaces both `RequestDocs` and `RequestMyIncome`, in parallel.
- Polly retries fire on simulated 5xx (try by temporarily setting `BaseUrl` to a non-existent host in `appsettings.Development.json` — restart required).

- `business.RecordAadeSyncProgress` enforces "only forward" — if you pass a lower mark, `LastAadeIncomingMark` does not regress.

**Verify in pgAdmin:**
- Rows in `Invoices` for incoming (keyed by `AadeMark`).
- Rows in `IncomeBookEntries` for outgoing (keyed by the `(BusinessId, CounterpartyAfm, IssueDate, DocumentTypeCode)` tuple).
- `Businesses.LastAadeIncomingMark` / `LastAadeOutgoingMark` advanced.
- `Businesses.LastAadeSyncAt` updated.

## Test 8: Disconnect AADE

**Goal:** confirm credentials are cleared + failure state is reset + audit fires.

**Steps:**
1. AADE page → **Αποσύνδεση** → confirm dialog.
2. Set breakpoints:
   - `src/Roivo.Application/Features/Aade/Commands/DisconnectAade/DisconnectAadeHandler.cs` → `Handle`.
   - `EncryptedCredentialStore.ClearAsync`.

**Watch for:**
- `ClearAsync` issues `UPDATE Businesses SET AadeUserIdEncrypted = NULL, AadeSubscriptionKeyEncrypted = NULL`.
- `business.ClearAadeSyncFailure()` runs (no point tracking failure on a disconnected business).
- `business.UpdateAsync` persists the cleared failure fields.
- `AuditAction.AadeDisconnected` written.
- Banner (if shown) disappears on the page after `RefreshBusinessAsync`.

**Verify in pgAdmin:**
- `Businesses.AadeUserIdEncrypted` / `AadeSubscriptionKeyEncrypted` are NULL.
- `Businesses.HasAadeFailure = false`.

## Test 10: Simulate AADE failure and verify banner

**Goal:** confirm the banner renders on both pages and that the conditional reads `Business.HasAadeFailure` correctly.

**Steps:**
1. In pgAdmin, simulate a stuck failure:
   ```sql
   UPDATE "Businesses"
   SET "HasAadeFailure" = true,
       "AadeLastFailureAt" = NOW() - INTERVAL '2 hours',
       "AadeLastFailureReason" = 'InvalidCredentials',
       "AadeFailureEmailSentAt" = NULL
   WHERE "Id" = '<your-business-id>';
   ```
2. Navigate to `/businesses/{id}/aade` — banner should appear above the connected-state panel.
3. Navigate to `/businesses/{id}/invoices` — same banner appears above the tab strip.
4. Set a breakpoint in each Razor page on the `@if (business.HasAadeFailure)` line and confirm the conditional evaluates `true`.

**Try the auto-heal:**
- Click **Συγχρονισμός τώρα** on a connected business. If sync succeeds, the handler runs `ClearAadeSyncFailure()`. The page's `RefreshBusinessAsync` re-reads — banner should disappear without a hard refresh.

## Test 11: Trigger the Hangfire failure-notification job

**Goal:** see the 24-hour notification email fire end-to-end.

**Steps:**
1. Make the failure stale (more than 24h):
   ```sql
   UPDATE "Businesses"
   SET "AadeLastFailureAt" = NOW() - INTERVAL '25 hours',
       "AadeFailureEmailSentAt" = NULL
   WHERE "Id" = '<your-business-id>';
   ```
2. Open `/hangfire` (dev only). Find the recurring job `aade-failure-notification`.
3. Set breakpoints:
   - `src/Roivo.Infrastructure/Jobs/AadeFailureNotificationJob.cs` → `Execute` first line.
   - The `_emailSender.SendEmailAsync(...)` call inside the foreach loop.
   - `business.RecordAadeFailureEmailSent()` immediately after.
4. Click **Trigger now** on the dashboard.

**Watch for:**
- `ListWithExpiredAadeFailureAsync` returns your business (and only failed ones past the 24h threshold whose `AadeFailureEmailSentAt` is null).
- `GetTenantPrimaryEmailAsync` returns the owner's confirmed email.
- Email body contains the business name, AFM, failure timestamp, the reason translated to Greek, and the reconnect URL `https://test.roivo.gr/businesses/{id}/aade` (or whatever `App:PublicBaseUrl` is configured to).
- `RecordAadeFailureEmailSent` sets `AadeFailureEmailSentAt`.

**Verify in pgAdmin:**
- `Businesses.AadeFailureEmailSentAt` is now non-null.

**Verify in Mailtrap:**
- Email arrived with subject "Πρόβλημα σύνδεσης AADE - Roivo".

**Trigger it a second time without resetting** — no email is sent (the `AadeFailureEmailSentAt` filter excludes already-notified businesses).
